# 9. CHALLENGES FACED

The project crossed groundwater science, data engineering, machine learning, web development, database security and cloud deployment. The main challenges, some of which changed the direction of the project, are listed below.

## 9.1 No ISR Data from India

ISR uranium mining is not carried out in India, so there is no Indian record of how an ISR operation affects groundwater. The project needed real values for the source concentration, the effect of restoration and typical operating settings, but none could be found locally.

### Mitigation Measures

- Searched global sources and selected the USGS Texas ISR records [@usgs_tx; @usgs_ops], following the mentor’s advice.
- Used the Texas data only for the chemistry of the source and for restoration results, never for rock or flow properties.
- Took all hydrogeology (rock type, flow, fractures, layers and background chemistry) from Jharkhand data.
- Stated clearly in the system and the reports that every site is hypothetical.

## 9.2 Limited Groundwater Monitoring Data

The measured groundwater quality record has only one sample per well, from one year (2023). Well depths are not recorded. Iron, arsenic and manganese were never tested, and 55 wells in the uranium belt were never tested for uranium. With such data, trends cannot be calculated and a plume cannot be learned from measurements.

### Mitigation Measures

- Used the measured data for what it can support: assessment against IS 10500 and background chemistry.
- Added the older 2000–2021 CGWB record [@nwdp] for trends in general chemistry.
- Created a separate “not tested” class so that missing data is never shown as safe.
- Turned the gaps themselves into a result: the monitoring-gap ranking and recommendations.

## 9.3 Early ML Models Learned the Wrong Thing

The ML pipelines of March to May 2026 appeared to perform well (R² of 0.69 on real rows). A detailed check in June showed that the real rows had no distance from any mine and no time since injection, because those values had been filled with one median value. The model was really predicting natural background uranium, not contamination spread. The distance relationship existed only in the project’s own synthetic data. This meant that several months of ML work could not meet the project’s objective.

### Mitigation Measures

- Accepted the finding and decided to rebuild instead of patching the old pipeline.
- Moved the physics into a transport engine based on published groundwater equations.
- Trained the ML model on the engine’s output, so that it learns physics, not artefacts of the data.
- Added strict validation (grouped folds, leave-aquifer-out and baselines) so that such a mistake would be caught.

## 9.4 Modelling Fractured Hard Rock

Most ISR and contaminant models are made for sandstone. Jharkhand’s uranium lies in fractured metamorphic rock, where water moves through cracks and chemicals soak into the rock between them. Important parameters such as the matrix storage ratio (β), fracture opening and matrix diffusion have never been measured in the Singhbhum shear zone.

### Mitigation Measures

- Added dual-porosity slowing and matrix diffusion from the published fractured-rock literature [@goltz1986; @tang1981].
- Reduced permeability with depth using district-wise NAQUIM evidence.
- Calculated β from the local porosities instead of using a fixed literature value.
- Listed all unmeasured constants and modelling choices in an assumption register (Assumptions page) and ran a sensitivity analysis to show which ones matter.

## 9.5 Errors Found in the Transport Model

Several errors were found in the engine during the review rounds. The most serious ones were: the travel distance was being measured to the corner of a calculation box instead of along the plume (422.8 m instead of 35.9 m at Jaduguda); the plume in fractured rock moved at the same speed for all chemicals; a term of the Ogata–Banks formula was missing, which made concentrations 17% to 42% too low; restoration was credited before it had actually happened; and the vertical screening moved a parcel of water instead of the dissolved chemical, so every chemical reached the shallow aquifer at the same time and the matrix storage that holds uranium back sideways had no effect upward.

### Mitigation Measures

- Carried out three review rounds, each with a written list of findings.
- Built an exact numerical reference solution and compared the engine with it on 240 cases.
- Fixed every confirmed error and pinned it with an automated test.
- Retrained the ML model after each fix that changed the training data.

## 9.6 A Borrowed Permeability Value

For most of the project a shear-zone transmissivity of 370 m²/day was used at the mines, described as coming from where the mines are. The recovered NAQUIM report for the belt showed that the three wells behind it (Kalapathar, Baharagora and Manusmuria) are in Tertiary sediments 51 to 58 km east of Jaduguda, and UCIL’s records ruled it out independently: it would force Turamdih to pump about 17.5 times the water it reports. The number had passed every review because it looked reasonable and its source had never been traced back to the well.

### Mitigation Measures

- Traced the value to the individual wells in the CGWB table and read their rock type.
- Replaced it with the measured maximum in the belt’s own rock (Kudada, 19 m²/day) and checked it against the mine discharges (Sections 4.4 and 7.4).
- Added the ISR-feasibility hypothetical as a separate, labelled answer, so that “what if the rock were more permeable?” is still answered without mixing it into the measured baseline.
- Re-pointed the engine tests that had used the old value to a fixture that keeps it.

## 9.7 Poor ML Accuracy for Radium

Radium hardly moves in the rock, so most of its training values are exactly zero or equal to the background. The ML model could not learn this well, and the radium travel-distance result stays below the project’s own accuracy target of 0.60.

### Mitigation Measures

- Reported the result openly instead of lowering the target.
- Kept the physics engine as the authority for all radium values.
- Checked that the radium uncertainty bands still cover at least 90% of cases.
- Listed a two-stage model (first “does it move?”, then “how far?”) as future work.

## 9.8 Data Quality Problems in Source Files

Several problems were found in the data files. The district and block boundaries had been stored with latitude and longitude swapped for months. Aquifer values were stored as text ranges such as “26 - 176” or “2-3%”. The Texas file had units rows, footnotes and one data-entry error (a pH of 795). The 2023 chemistry file balanced perfectly because sodium had been calculated from the other ions. A test record added during field-observation testing was later found in the deposit data.

### Mitigation Measures

- Fixed the swapped coordinates with a database migration and corrected the loader.
- Wrote parsers for range values, detection limits (“<.001”) and uncertainty notation (“1044±5”).
- Added row-count checks so that parsers cannot silently drift.
- Added a hydrochemical quality check and reported its limits honestly.
- Removed the test record through the dataset manager and checked the live database.

## 9.9 Security Controls That Failed Silently

Some controls looked correct but did nothing. Row-level security depends on a setting that lasts only until the end of a database transaction; code that saved data and then continued writing lost it, so the database quietly returned nothing. Because of this, publishing a screening never raised any alerts, and the test database, which had no security policies, could not catch it. The rate limit was configured, but the component that enforces it had never been installed. The measured-exceedance scan checked only uranium above 30 ppb, which never happens, so it matched zero wells. Earlier, the signup page accepted a role chosen by the user, and admin login details were found built into the portal code.

### Mitigation Measures

- Found the problems by counting rows in the live database and measuring each control, instead of trusting the logs or the configuration.
- Wrote all values in the first insert and added the missing update permission for alerts.
- Installed the rate-limit middleware and added a test that makes 30 quick logins and checks that they are refused.
- Changed the scan to check all health substances and tiers.
- Closed the signup hole, moved to five roles with database enforcement, and added a build guard that fails if any secret reaches the portal code.

## 9.10 Free Cloud Hosting and Email Delivery

The backend runs on a free tier that sleeps when idle (about 53 seconds to wake), and one engine run takes about 4 seconds there against 0.3 seconds locally. One long request was cut off by the hosting gateway. Email delivery needed several attempts: the host silently blocked port 587, the relay needed its own login name, its IP allow-list rejected the host’s changing address, and a failed email was never retried.

### Mitigation Measures

- Split long requests into smaller ones and walked every screen on the deployed system.
- Kept the design simple (engine inside the backend, no extra services) to fit the free tier.
- Switched to port 2525, used the relay’s own SMTP login, and removed the IP restriction.
- Made failed emails retry, with a test for it.

## 9.11 Learning a New Subject

The project needed knowledge of hydrogeology, groundwater chemistry, contaminant transport and mining regulation, none of which is part of the Information Technology course.

### Mitigation Measures

- Self-study of textbooks, government reports and research papers from the first month.
- Used published equations and standards instead of inventing new ones.
- Wrote down every assumption and its source in the code and documents.
- Discussed the direction of the work with the mentor.

## 9.12 Lessons Learned

The most important lessons were:

- A good accuracy score does not prove that a model has learned the right thing; the data behind it must be checked.
- A control that looks correct in the code may still do nothing; it must be measured.
- Missing data should be shown as missing, never as safe.
- Every assumption should be written down with its source, so that it can be checked and replaced later.
- A value that looks reasonable should still be traced back to the well or sample it came from.
