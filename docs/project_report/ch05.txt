# 5. TOOLS & TECHNOLOGIES USED

The development of JalDrishti involved programming languages, a web backend framework, a spatial database, scientific and machine learning libraries, a web frontend framework, cloud hosting services, and open datasets from several agencies. Together these made it possible to build a system that runs a groundwater model, trains and serves ML models, stores spatial data securely, and presents the results through a web portal. All the software used is open source or has a free tier, and no hardware was purchased.

### Python

Python was used for most of the project. The physics engine, the synthetic data generator, the ML training pipeline and the backend server are all written in Python, because it has strong scientific libraries (NumPy, SciPy, pandas) and good support for web APIs (FastAPI).

### TypeScript

TypeScript was used for the portal. Its type checking catches mistakes when the shape of the data sent by the backend changes, which happened often during development.

### FastAPI

FastAPI was chosen because it is fast, supports asynchronous code, and creates interactive API documentation automatically. The backend was first started in Node.js in November 2025 and moved to FastAPI in December 2025. Using Python for both the backend and the ML code kept the whole system in one language.

### Authentication and security

Users log in with JWT tokens. Passwords are hashed with argon2. The user’s role is read again from the database on every request instead of being trusted from the token. Rate limiting protects the login endpoint from repeated password guessing.

## 5.3 Database

TABLE: Database technologies
|{w=5,11}|
|Technology|Purpose|
|PostgreSQL 16|Main relational database|
|PostGIS|Spatial data types and queries (points, polygons, “which block contains this well”) [@postgis]|
|Row-Level Security (RLS)|Database-level rules that decide which rows each role can read or change|
|Neon|Managed cloud hosting for the PostgreSQL database|

PostGIS was essential because almost everything in the project is spatial: wells, blocks, districts, aquifers, deposit outlines and plume footprints. For example, an alert is raised for a block when the plume footprint polygon intersects the block polygon, which is a single PostGIS query. Row-level security gives a second line of protection: even if an API check were missed, the database itself refuses to show a resident a hypothetical site coordinate or a draft screening.

### XGBoost

XGBoost was chosen over the Random Forest and SVM models named in the proposal for three reasons: it supports quantile (percentile) training directly, it allows monotone constraints so that physical rules can be built into the model, and it trains quickly (all ten models train in about 200 seconds). Random Forest and logistic regression were used in the earlier pipelines of March to May 2026 (Chapter 6).

## 5.9 Technology Integration

All the tools above work together as one system. The overall technology workflow can be shown as:

FLOW: Open Datasets (CGWB, GSI–NRSC, IAEA, USGS, Copernicus) >> Python Data Preparation (pandas, GeoPandas, NumPy) >> Physics Engine (NumPy, SciPy) >> ML Surrogate (XGBoost, scikit-learn, SHAP) >> FastAPI Backend + PostgreSQL / PostGIS >> React + Leaflet Portal >> Residents and Officials (web portal and email alerts)

The selected tools gave a low-cost, flexible and maintainable platform for building a groundwater contamination screening system that can be used anywhere in Jharkhand.
