## 1. The five roles

Two audiences drive the model (`PRODUCT_DESIGN.md` §2): **government officials** who need to know
which aquifers are vulnerable, and **common users** who need to know whether the water near them is
at risk. The other three roles exist to serve those two.

| Role | Who holds it | Exists to |
|---|---|---|
| `admin` | BIT Sindri / TEXMiN, the system owner | Operate the platform: accounts, ingest, dataset promotion, everything |
| `regulator` | **CGWB / SPCB / district officer** — the primary government user | Read every site, publish and archive them, export signed reports, resolve alerts, read the audit log |
| `analyst` | Technical staff and researchers | Run and save scenarios against sites their organisation owns |
| `field_officer` | Station and well data collectors | Submit field observations — ore sightings, water quality, groundwater levels — for review (§3). Never writes authoritative data directly |
| `citizen` | **Common user**, resident of a mining district | See district/block-level risk in plain language. Nothing precise |

### The distinctions that actually matter

Four lines separate these roles. Everything else is detail.

**1 · `citizen` vs everyone else — the coordinate line.**
This is the only distinction with a *policy* reason rather than a convenience reason. Every ISR site
in this system is **hypothetical**; none exists. Publishing a precise coordinate for a speculative
uranium mine next to a named village invites it being read as a real plan, with land-value and panic
consequences the project has no mandate to cause. So citizens get **block-level aggregation**;
everyone else gets points.

In code this is `STAFF_ROLES` in `app/dependencies.py` — the four working roles — and it is enforced
twice: by `require_staff` at the API, and by the `isr_points_read` RLS policy at the database, so a
service bug cannot leak what the guard was meant to withhold. `viewer`, the legacy role migrated by
`0008`, is treated as `citizen` on both paths.

**2 · `regulator` vs `analyst` — who decides vs who investigates.**
An analyst *explores*: runs scenarios, saves them, compares them. A regulator *decides*: marks a site
published or archived, signs an export, closes an alert. An analyst may generate a frightening
number; only a regulator can make it official. This is why `GET /audit` is regulator-and-admin —
analysts appear in the log and cannot read it.

**3 · `field_officer` vs `analyst` — writing observations vs writing interpretations.**
A field officer adds *measurements*: a water level, a sample. They never touch model inputs,
scenarios, or site definitions. An analyst never uploads raw field data. Keeping these apart means a
data-entry mistake cannot silently become a modelling assumption, and it keeps the provenance chain
honest about who observed what.

**4 · `admin` vs `regulator` — the platform vs the domain.**
Admin is an operator role: accounts, ingest, deletion. Regulator is a domain-authority role. A
regulator should never need to create a user, and an admin has no standing to publish a finding.
Deletion is admin-only throughout, because the design requires soft-delete and archival rather than
destruction.

## 3. Field observations — the review workflow

A field officer's job is to record what is discovered *after* the initial datasets were loaded: a
new uranium ore outcrop, a water-quality reading, a groundwater level. Their submissions must not
become authoritative on their own word, and must never reach a contamination calculation unreviewed.

```
field officer                 admin / regulator              authoritative data
──────────────                ─────────────────              ──────────────────
POST /field-observations
   → status: pending  ────────►  GET /field-observations
   (nothing changes yet)         ?status=pending
                                     │
                                     ├── /approve ──────────►  row written
                                     │                         (+ applied_id)
                                     └── /reject   ─────────►  nothing written
```

**Why proposals live in their own table.** The alternative — a `status` column on `water_samples` —
fails open: the guarantee would then depend on every present and future query remembering
`WHERE status = 'approved'`, and the first one that forgets feeds unreviewed field data into a
contamination number. A pending proposal is simply **not in `water_samples`**, so no query can see
it by accident, including queries nobody has written yet.

**What stops a bad submission from becoming authoritative:**

| Guard | Where |
|---|---|
| Pending rows are absent from the authoritative tables | schema shape |
| A submitter can never review their own proposal | `ck_field_obs_no_self_review`, a CHECK constraint — not just a service test |
| Only `admin`/`regulator` may approve or reject | `require_regulator_or_admin` |
| A payload may only set allowlisted columns | `ALLOWED_FIELDS` per type — keeps the approval path away from `synthetic`, ids, and anything unreviewed |
| Approving a stale proposal cannot clobber a newer edit | row fingerprint taken at submit, rechecked at approval → `409` |
| A decided proposal cannot be re-approved | status check → `409`, so a double click cannot double-apply |
| `ore_observations` is writable only under the system bypass | RLS policy — **no role**, including admin, can insert an authoritative ore record without going through a review |
| One officer cannot read another's unreviewed submissions | `field_obs_read` RLS policy, scoped by `app.current_user_id` |

**Provenance.** Every transition writes an audit row carrying `old` and `new` payloads, the
submitter, the reviewer and the decision note. The proposal row itself keeps `previous` and
`proposed` permanently, so a value on the map can always be traced back to who observed it and who
approved it. Refused approval attempts are audited too, as `access_denied`.

**Three states, not two.** Approval makes an observation authoritative in the portal; only an
admin-triggered dataset sync (`POST /dataset-sync/ore`) puts it in front of the physics engine, which
reads `Datasets/`. The UI distinguishes 🔴 pending review, 🟡 approved but pending sync, and 🟢
approved and in the model, and `GET /dataset-sync/status` carries the count. See
`PRODUCT_DESIGN.md` §3.6 for why the gap is shown rather than closed automatically.

**The map keeps them apart.** `GET /field-observations/map` returns `pending` and `authoritative` as
two separate collections rather than one list with a flag, because a merged list invites a client to
draw unreviewed field input as though it were confirmed.

## 4. How authorization is enforced

Three layers, each of which can independently refuse a request.

**API guards** — `app/dependencies.py`. `require_roles(...)` builds a dependency that compares the
caller's role against an allowed set. The role is **re-read from the database on every request**
rather than trusted from the JWT claim, so demoting a user takes effect immediately instead of at
token expiry.

**Row-level security** — migration `0009`. Policies on `isr_points` and `audit_log` read three
per-transaction settings, applied by `get_db` and raised to the caller's identity by
`get_current_user`:

| Setting | Meaning |
|---|---|
| `app.current_role` | the caller's role, `''` when unauthenticated |
| `app.current_org_id` | the caller's organisation |
| `app.bypass_rls` | `'on'` for trusted internal work (seed, ingest jobs) |

`SET LOCAL` scopes these to the transaction, so a pooled connection cannot leak one request's
identity into the next. `get_db` opens **unauthenticated** and is only raised once identity is
verified — so a route that forgets its auth dependency gets a session the policies treat as
anonymous. The failure mode is a denied read, not a leak.

**Database privileges** — the API connects as `jaldrishti_app`: `NOSUPERUSER`, `NOBYPASSRLS`,
`NOCREATEDB`, `NOCREATEROLE`, with `SELECT/INSERT/UPDATE/DELETE` and nothing else. `CREATE` on
schema `public` is revoked (Postgres grants it to the `PUBLIC` pseudo-role by default, which
quietly contradicted "DML only" until it was taken away), so the role cannot create a table, alter
one, or drop a policy that constrains it. `scripts/create_app_role` **refuses to finish** if any of
those checks fails. Migrations connect separately as the owner via `MIGRATION_DATABASE_URL`.

Verified state of the cutover:

| Check | Value |
|---|---|
| API connects as | `jaldrishti_app` |
| `rolsuper` / `rolbypassrls` / `rolcreatedb` | `false` / `false` / `false` |
| `CREATE` on schema `public` | `false` |
| Migrations connect as | `postgres`, via `MIGRATION_DATABASE_URL` |
| Startup report | `Row-level security active: 4 policies, connected as 'jaldrishti_app' (no bypass)` |

> **Why the third layer is not optional.** Postgres skips row-level security entirely for a
> superuser or any role with `BYPASSRLS`. While the API connected as `postgres`, a table with
> `FORCE ROW LEVEL SECURITY` and a `USING (false)` deny-all policy still returned **every row** —
> verified, not assumed. Layer 2 is inert without layer 3, and `app/main.py` logs a loud warning at
> startup if that combination ever returns.

**One RLS semantic to know:** a write blocked by a `USING` clause affects **zero rows and does not
raise**. Only `WITH CHECK` violations error. Denials are therefore *silent* — anything built to
detect tampering by catching an exception will never fire. The audit log's append-only guarantee has
this shape: no `UPDATE` or `DELETE` policy exists on `audit_log`, so both affect nothing, for every
role including `admin`.

### Reading the tallies

- **admin 50/54** — not 54/54, because `POST /auth/login` and the two public routes are counted as
  `○` (no authentication) rather than as an admin permission.
- **regulator 28/54** — reads everything, and now approves or rejects field observations. The
  publish/archive/export/alert endpoints are still P5 and P8.
- **analyst 38/54** — the widest working role, and the one to watch: it can still ingest (D-2), and
  it can read the review queue but not decide on it.
- **field_officer 27/54** — reads, plus the three write routes that make the role real: submit,
  withdraw, and reading back its own queue. Still zero direct writes to authoritative tables.
- **citizen 1/54** — `GET /auth/me`, by design until P6.
